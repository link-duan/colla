# Submissions and commits

Submission is a controlled request generated by SyncSession. ServerMessage is a controlled
Commit or Rejection generated by Authority. Use their encode/decode methods at transport
boundaries instead of constructing plain objects that resemble protocol fields.

## Request identity

A Submission carries documentId, clientId, sequence, baseRevision and change. Sequence
and revisions are bigint u64 values in JavaScript. Together, the document/client/sequence
identify the request; ElementIds identify content and serve a different purpose.

Request identity remains fixed until confirmation. See [Retries](./retries#retry-the-original-bytes)
for the distinction between the original request and its rebased working Change.

## Confirmation and buffering

A formal Commit includes the sender identity, sequence, assigned revision and accepted
Change. Its sender receives it through the same receive API as other clients. It confirms
the request without applying the already-visible local intent twice and promotes any
buffered changes to the next request.

A request that rebases to Noop still receives a revision and a receipt. This differs
from a local Noop transaction, which creates no outgoing request. Observe the session
state channel to see acknowledgement-only progress.

## Rejections

Check ServerMessage.type before using change or revision. Rejection provides reason;
those optional fields are not guaranteed on every message. Let SyncSession.receive
perform its state transition, then surface recoveryReason and preserved work as described
in [Recovery](./recovery). See [Protocol reference](/reference/protocol) for object fields.
